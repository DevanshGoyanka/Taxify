# ITR-3 Schedule-by-Schedule Implementation Tracker

**This is the single source of truth for the ITR-3 schedule-wise implementation push.** Updated after every schedule is completed end-to-end. Supersedes `Docs/ITR3_V2_PIPELINE_PRODUCTION_PLAN.md` and `Docs/ITR2_ITR3_V2_PIPELINE_PRODUCTION_PLAN.md`'s Phase 8 for status purposes (their PDF↔schema reconciliation table, reproduced below, remains valid reference material and is not being redone).

## Ground rules for this push

1. **One schedule at a time, in official PDF print order** (the table below). No skipping ahead.
2. For each schedule: read the official ITR-3 form PDF section + the official JSON schema block, then implement **every mandatory and optional field** — schema → draft mapper → calculator → ITD JSON builder. A schedule is not "done" until data flows for real from a `ReturnDraft` through to schema-valid JSON, not just until the builder can serialize a hand-constructed object.
3. **Validators are explicitly out of scope for this entire push.** `app/engine/validators/itr3/` is not touched until every schedule below is done and a separate validator pass begins. Do not add, remove, or edit any ITR-3 validator rule while working through this tracker.
4. **ITR-3 only.** If a defect is found in already-shipped ITR-1/ITR-2/ITR-4 code along the way, it is flagged in the "Cross-form issues found, not fixed" log at the bottom of this document and the user is asked explicitly before anything in those forms' code is touched. Never edit ITR-1/ITR-2/ITR-4 code as a side effect of ITR-3 work.
5. Frontend work in this push is limited to what's needed for real end-to-end data flow (wiring a field to the draft, fixing a mapping bug) — **not** visual/UX redesign, which is tracked separately (`Docs/FRONTEND_UI_UX_REDESIGN_AUDIT_AY2026_27.md`) and deliberately deferred.
6. After each schedule: run the full regression suite, confirm no new failures beyond the established baseline, update this tracker's status table and add a dated "Fix status" note under that schedule, then commit.

## Schedule-by-schedule fix log

### Schedule 1 — Personal Information (A1–A18) — ✅ closed 2026-09-17

**What was found** (comparing `Docs/ITR3_FIELD_BY_FIELD_GUIDE_1_PERSONAL_INFO_TO_HP.md` §1 and the official schema's `PersonalInfo`/`AlternateAddress` definitions directly against `app/engine/itd/itr3.py::_parta_gen1`):
- A6a (building/village name) and A7a (road/street) were captured nowhere — the builder hardcoded `ResidenceName`/`RoadOrStreet` to `""` unconditionally.
- A16 (Aadhaar) was read by `_parta_gen1`'s signature but never actually sourced from `ITR3Input` in the canonical path — always absent from real filings.
- A17's office/residence phone (schema `Address.Phone`) had no code path at all; its secondary-mobile columns (`CountryCodeMobileNoSec`/`MobileNoSec`) were hardcoded to `0`/`0` unconditionally.
- A18's secondary email (`EmailAddressSec`) was never emitted.
- **A5b–A13b, the "Secondary Address"**: `SecondaryAdd` was hardcoded `"N"` regardless of the taxpayer's actual declaration, and — the most serious finding — whenever `secondary_add == "Y"` was forced via a non-canonical caller, `AlternateAddress` was populated as a **literal copy of the primary address**, not real secondary-address data. There was no source data path for a genuine alternate address anywhere in the pipeline.
- Root cause for all of the above: `app/schemas/itr3.py`'s `ITR3Input` had no fields at all for any of this (only the eight primary-address scalars), and `app/engine/draft_to_itr3_input.py` never read the corresponding `ReturnDraft.personal.*` fields — even though every one of those fields (`aadhaar`, `secondaryEmail`, `secondaryMobile`(+country code), `landlineStdCode`/`landlinePhoneNo`, `residenceName`, `roadOrStreet`, `secondaryAddressDifferent`, `alternateAddress`) already existed on the shared `PersonalInfo` draft model. **No frontend/draft-schema changes were needed** — this was purely a backend mapper + builder gap.

**What was fixed:**
- `app/schemas/itr3.py`: added `residence_name`, `road_or_street`, `zip_code`, `mobile_country_code`, `assessee_aadhaar`, `office_phone_std_code`, `office_phone_no`, `secondary_mobile_country_code`, `secondary_mobile_no`, `secondary_email`, `secondary_address_different`, and the nine `alternate_*` fields to `ITR3Input`.
- `app/engine/draft_to_itr3_input.py`: mapped all of the above from `draft.personal.*`/`draft.personal.alternateAddress.*` (soft/optional, matching the mapper's existing style for this section — hard requiredness stays the builder's job, as it already was for the original 8 fields).
- `app/engine/itd/itr3.py`: `_parta_gen1()`/`build_itr3_json()` rewritten to emit every field for real: `ResidenceName`/`RoadOrStreet` from sourced data; `AadhaarCardNo` from the typed input; `Address.Phone` emitted only when a real STD code + number exist; secondary mobile/email sourced for real; `SecondaryAdd` reflects the taxpayer's actual flag; `AlternateAddress` built from genuinely distinct secondary-address data, never copied from the primary address. Added a fail-closed check: if `secondary_address_different` is True but the required alternate-address fields weren't actually sourced, `build_itr3_json` now raises rather than silently omitting or fabricating the block. `AlternateAddress.PinCode`/`ZipCode` are only emitted when real (neither is schema-required — no fabricated PIN default was introduced for the new code, unlike the pre-existing primary-address fallback which was left as dead-path legacy scaffolding, see below).
- Deliberately **not** touched: the primary `Address`'s existing fabricated-default kwargs (`locality: str = "Locality"`, `pin_code` falling back to `110001`, etc.) on `build_itr3_json`'s legacy (`typed_input=None`) call path — every real canonical caller already passes `typed_input`, which hard-requires these via the pre-existing `required_identity` check before `_parta_gen1` is ever reached, so this fallback code is effectively dead in production; changing pin_code's required-ness policy (e.g. to support a foreign-only ZIP-code address) is a separate design decision, not evidenced as broken today, and was left alone to keep this fix scoped to real field-completeness, not a required-ness policy change.

**Verification**: two new tests in `tests/test_itr3_canonical_foundation.py` — `test_itr3_personal_info_optional_fields_reach_typed_input_and_json` (every new field set on a realistic draft, asserted present in both `typed_input` and the emitted JSON, validated against the official `PersonalInfo` schema sub-definition directly via `jsonschema.Draft4Validator` — scoped to this schedule since the full document doesn't validate yet yet, pending Schedules 5/8/9/25/26/24 etc.) and `test_itr3_secondary_address_flag_without_data_fails_closed` (confirms the new fail-closed guard). Both confirmed genuinely failing pre-fix via `git stash`. Full combined regression (`test_itr1/2/3/4_*.py` + filing-gateway/AMT/CYLA/BFLA/capital-gains suites): 1313 passed, same 10 pre-existing baseline failures plus the one already-flagged, pre-existing, unrelated ITR-2 regression (see "Cross-form issues" above) — no new failures.

**Correction found during Schedule 2 work (2026-09-17), applied retroactively to Schedule 1**: while reading ITR-2's own `_part_a_gen1`-equivalent builder as a reference, found a live-UAT-verified fact ITR-2's own code comment documents (2026-09-13, PAN GOYPT2026A): ITD's real Type-2 `validateItr` **rejects an entirely-absent `AlternateAddress` block**, regardless of the `SecondaryAdd` flag's value — even though neither is schema-required. Schedule 1's original fix omitted `AlternateAddress` whenever the taxpayer had no genuinely distinct secondary address, which — since ITR-3 shares the identical `PersonalInfo`/`AlternateAddress` schema shape with ITR-2 — would almost certainly hit the same live rejection. Revised to match ITR-2's proven fallback exactly: `SecondaryAdd` is now always `"Y"`, and `AlternateAddress` is always emitted, falling back to a copy of the primary address when no genuinely distinct one exists (the fail-closed guard for "declared different but didn't provide one" stays). Also found and fixed, while reading the schema's `Status` enum for A14: `assessee_status` (A1-A18's own Individual/HUF flag) was **never wired at all** — `build_itr3_json` never derived it from `typed_input`, so every canonical filing silently emitted `"I"` regardless of the real `draft.personal.assesseeStatus`. Added `ITR3Input.assessee_status`, mapped from the draft, and wired into the canonical builder path. Both corrections covered by `test_itr3_no_secondary_address_still_emits_alternate_address_as_primary_copy` (new) and the existing Schedule 1 tests, all confirmed passing; full detail in the Schedule 2 entry below.

### Schedule 3 — Audit Information (A20) — ✅ closed 2026-09-17

**What was found**: `AuditInfo` (both the `app/schemas/itr3.py` typed model and the `_parta_gen2()` builder) covered only 5 of roughly 25 real schema fields. Two of those five weren't even real: `AgrOFAllAmtsRcvd`/`AgrOFAllPayMade` (A20(a2ii)/(a2iii), the cash-receipt/payment percentage question that determines whether a mid-size taxpayer is 44AB-liable) were **hardcoded to `"Upto5Per"` unconditionally**, regardless of the actual return — a return where the real answer was "more than 5%" (the answer that actually *triggers* audit liability) would have silently disclosed the wrong, audit-avoiding answer. Entirely absent: the turnover band (a2i), the 44AB-liability reason (b(i)/(ii)/(iii) + the `BiiDetails` presumptive-section sub-flags), the entire audit-report detail block (c(1)-(4): furnish date, acknowledgement number, auditor name, auditor PAN/Aadhaar), the section-92E audit detail (d(ii): date + acknowledgement, distinct from merely being *liable* under 92E), and both "other audit report" tables (d(iii) — other-section audit reports for 10A/10AA/44DA/50B/80-IA-family/80JJAA/80LA/115JC; (e) — audit under an Act other than the Income-tax Act, e.g. Companies Act/GST/SEBI Act).

`app/schemas/return_draft.py`'s `ITR3AuditInfo` (plus its two row types, `OtherAuditReportEntry` and `AuditUnderOtherActEntry`) already captures every one of these fields in full — confirmed, as with Schedules 1-2, this was purely a backend mapper + builder gap, no frontend work needed.

**What was fixed:**
- `app/schemas/itr3.py`: extended `AuditInfo` from 5 to 24 fields, covering the full A20(a)-(e) list.
- `app/engine/draft_to_itr3_input.py`: `_audit_info()` rewritten to extract every field from both of this mapper's existing two data sources — the raw official-schema-shaped "workspace" object (`draft.itr3BusinessWorkspace.core["PartA_GEN2"]["AuditInfo"]`, when a UI editor has written directly in CBDT shape) and the canonical typed `draft.itr3AuditInfo` fallback — matching the dual-path pattern this function already had for the 5 original fields, just extended to the other 19.
- `app/engine/itd/itr3.py`: `_parta_gen2()` rewritten to emit every field for real, each one only when the taxpayer's actual data supports it (the audit-report detail block only when `audited_by_accountant` is true; the 92E detail only when both the date and acknowledgement number are genuinely present; both array tables built from real entries, empty rows filtered out) — never fabricated, matching this schedule's own "omit, don't guess" discipline. Also fixed the `AuditAccountantFlg` field, which was previously wired to `audit.account_audited` (the SAME boolean already used for the separate, differently-named `AccountAuditFlag` field) — now correctly reads the draft's own distinct `audited_by_accountant` fact.

**Verification**: two new tests — `test_itr3_audit_info_full_44ab_disclosure_reaches_json` (every field set on a realistic 44AB/92E-audited taxpayer, asserted through to the JSON, including both array tables) and `test_itr3_audit_info_not_audited_omits_report_detail_not_fabricates` (a non-audited taxpayer gets no fabricated audit-report detail — a confirmation test: this specific behavior was already correct before the fix too, since those fields were simply never emitted at all; it now locks in that the *fix* didn't accidentally start fabricating them once real data-sourcing was added elsewhere in the same function). Both validated against the official `AuditInfo` schema sub-definition; the first confirmed genuinely failing pre-fix via `git stash`. ITR-3 suite: 64 passed (up from 62). Full combined regression: 1319 passed, same 10-failure baseline + the one already-flagged unrelated ITR-2 regression — no new failures.

### Schedule 4 — Nature of Business or Profession — ✅ closed 2026-09-17

**What was found**: a small schedule (just `Code`/`TradeName1`/`Description` per row), but with two real bugs, not just a completeness gap.
1. **`TradeName1`** ("Trade name of the proprietorship, if any") was captured on the draft (`ITR3NatureOfBusiness.tradeName`) but had **no field on the typed `NatureOfBusiness` schema at all**, and both mapper code paths silently dropped it — confirmed directly: the pre-existing test `test_itr3_builder_maps_parta_gen2_workspace` had been setting `tradeName="Tech"` on its own test draft since before this push and never noticed it never reached the output, because the test never asserted on that field.
2. **Three legitimate CBDT business-nature codes were silently dropped from every return that used them.** The official schema enum includes three disambiguation codes with an `_N` suffix — `16019_1` ("Medical Profession", distinct from the base `16019`), `20023_1` ("Sports Management"), `21008_1` ("Event Management"). Both the mapper's row filter (`row.code.isdigit()` / `str(...).isdigit()`) and the typed `NatureOfBusiness.code` field's own Pydantic pattern (`^[0-9]{5}$`) rejected any code containing the underscore — meaning a doctor, sports manager, or event manager correctly selecting their actual, official business-nature code would have that row either silently filtered out of the mapped list, or (if constructed directly) fail Pydantic validation outright.

**What was fixed:**
- `app/schemas/itr3.py`: `NatureOfBusiness.code`'s pattern widened to `^[0-9]{5}(_[0-9]+)?$`; added the missing `trade_name` field.
- `app/engine/draft_to_itr3_input.py`: added a shared `_NATURE_OF_BUSINESS_CODE` regex (`[0-9]{5}(_[0-9]+)?`) replacing the `.isdigit()` filter in both mapper paths (workspace raw-JSON and canonical `draft.itr3NatureOfBusiness`), and wired `trade_name` through both.
- `app/engine/itd/itr3.py`: `_parta_gen2()`'s nature-of-business row construction rewritten to emit `TradeName1` when present, and — a related correctness fix caught while touching this code — `Description` is now omitted (not emitted as `""`) when absent, since the schema's own `nonEmptyString` constraint on that field means an empty string would have failed official schema validation the moment a row had no description at all.

**Verification**: two new tests — `test_itr3_nature_of_business_trade_name_reaches_json` and `test_itr3_nature_of_business_disambiguated_codes_not_silently_dropped` (all three `_N`-suffixed codes survive the mapper and reach the JSON) — both validated against the official `NatOfBus` schema sub-definition and confirmed genuinely failing pre-fix via `git stash`. The pre-existing `test_itr3_builder_maps_parta_gen2_workspace` needed a one-line update to its own expected output, since its existing test data (`tradeName="Tech"`) had been silently exercising the bug without asserting on it. ### Schedule 5 — Part A-BS (Balance Sheet) — ✅ closed 2026-09-17

**What was found**: this is the schedule the earlier status investigation flagged as the biggest known gap, and it was — the typed `BSOfficial` tree was missing five entire required sub-blocks the schema demands with a `default: 0` (meaning they must always be present, unlike a genuinely optional disclosure): **`Investments`** (long-term + trade investments, form item 2), **`MiscAdjust`** (misc. expenditure / deferred tax asset / accumulated losses, form item 4), **`LoanAdv`** (loans and advances, form item 3b), **`NetCurrAsset`** (form item 3e — explicitly documented in the schema as "can be negative"), and **`NoBooksOfAccBS`** (form item 6, the entire "no account case" alternative). Directly confirmed live: a minimal draft with no balance-sheet data at all produced a `PARTA_BS` failing official schema validation with over a dozen missing-required-property errors (`FundApply.Investments`, `FundApply.MiscAdjust`, `CurrAssetLoanAdv.{CurrAsset,LoanAdv,CurrLiabilitiesProv,NetCurrAsset}`, `FixedAsset.{GrossBlock,Depreciation,NetBlock,CapWrkProg}`, `FundSrc.{LoanFunds,DeferredTax,Advances}`, `PropFund.{PropCap,ResrNSurp}`) — the codebase's own `itr3_preparation.py` had deliberately excluded this schedule from its "complete" list for exactly this reason.

Two further real bugs surfaced while closing this out, neither previously caught because a full schema validation of this schedule had apparently never actually been run before this push:
1. **`BSLoanGroup` (secured loans) had the wrong shape, not just missing fields.** The schema nests `FrmBank`/`FrmOthrs`/`TotRupeeLoan` under a `SecrLoan.RupeeLoan` sub-object; the typed model had them as flat siblings of `ForeignCurrLoan`/`TotSecrLoan`. Every secured-loan disclosure this codebase has ever emitted would have failed live schema validation with "Additional properties are not allowed" plus "'RupeeLoan' is a required property" — hidden until now behind the more obvious missing-block failures above.
2. **`TotLoanFund`** (`FundSrc.LoanFunds.TotLoanFund`, required) was being populated via `dict.pop("TotLoanFund", 0)` against a dict that could never actually contain that key (no typed field produced it) — always silently `0`, regardless of the real secured+unsecured loan totals.
3. **`PropCap`/`TotPropFund`** (proprietor's capital) had an incorrectly-strict `ge=0` constraint — the official schema places no minimum on these two fields specifically, a real, expected case for a business whose accumulated losses exceed contributed capital.

**What was fixed:**
- `app/schemas/itr3.py`: added `BSLongTermInv`, `BSTradeInv`, `BSInvestments`, `BSLoanAdvances`, `BSMiscAdjust`, `BSNoBooks`, and `BSRupeeLoan` (the last replacing `BSLoanGroup`'s flat fields with the correctly-nested shape); wired all seven into `BSOfficial`; removed the incorrect `ge=0` from `BSProprietorsFund.capital`/`.total`.
- `app/engine/draft_to_itr3_input.py`: `_balance_sheet()` extended to extract every new sub-block from the raw workspace JSON path. **The legacy fallback path (`draft.itr3BalanceSheet`, the simple flat summary model used when no rich workspace exists) previously never constructed a `BSOfficial` at all** — `official` was always `None`, silently routing every such filer through the builder's most minimal (and, per above, most broken) code path. Now builds a complete `BSOfficial` there too, placing the flat aggregate values (no finer breakdown exists in this simpler model) into each sub-group's own total field, and wires in the already-existing-but-never-used `noBooksOfAccounts`/`noBooksSundryDebtors`/etc. fields.
- `app/engine/itd/itr3.py`: `_parta_bs()` rewritten — the old minimal fallback branch (reachable whenever `official is None`) is now unreachable in practice (both mapper paths guarantee `official` is populated) and replaced with a fail-closed `ValueError` guard rather than silently emitting an incomplete tree; `Investments`, `LoanAdv`, `MiscAdjust`, `NetCurrAsset`, and `NoBooksOfAccBS` (when present) are all now popped/emitted for real; `TotLoanFund` is now genuinely computed as `secured_total + unsecured_total`.

**Verification**: four new tests — `test_itr3_balance_sheet_minimal_draft_now_schema_valid` (the exact minimal-draft case that failed live during the earlier status investigation, now validated clean against the full official `PARTA_BS` schema definition, not just a scoped sub-check), `test_itr3_balance_sheet_workspace_investments_and_misc_adjust_reach_json` (every new sub-block, real values, through to the JSON), `test_itr3_balance_sheet_no_books_case_reaches_json` (form item 6), plus the pre-existing `test_itr3_mapper_prefers_workspace_balance_sheet_over_legacy_fields` continuing to pass unchanged. Three of the four confirmed genuinely failing pre-fix via `git stash`. ITR-3 suite: 69 passed (up from 66). Full combined regression: 1324 passed, same 10-failure baseline + the one already-flagged unrelated ITR-2 regression — no new failures.

### Schedule 6 & 7 — Part A-Manufacturing Account / Part A-Trading Account — ✅ closed 2026-09-17

Closed together: both schedules share one mapper function (`_business_accounts()`), one pair of sibling schema classes, and are architecturally a matched pair on the official form itself (Manufacturing Account's own output, form item 3 "Cost of Goods Produced", feeds directly into Trading Account's item 11 "Cost of goods produced — Transferred from Manufacturing Account"; both share one combined header instruction on adjacent PDF pages).

**What was found**: contrary to the tracker's own prior-finding note ("generic key-lookup passthrough, not individually typed"), the *frontend* was already fully built out — `ITR3BusinessCoreManager.tsx` is a dedicated, official-schema-driven editor (not a generic fallback) covering every scalar, nested object, and repeatable-row field for both schedules, including calculated read-only totals. The generic-passthrough problem was entirely on the *backend*:
1. **`ManufacturingAccount`/`TradingAccount` (`app/schemas/itr3.py`) were untyped `dict[str, Decimal]` bags**, not individually typed models — no nested structure, no array support, nothing schema-checkable at the Python level.
2. **The mapper's `_decimal_map()` helper silently dropped every nested object** (`if not isinstance(item, Mapping)`) when flattening the raw workspace JSON — meaning `TradingAccount.ExciseCustomsVAT` (duties on sales, form item 4C) and `TradingAccount.DutyTaxPay.ExciseCustomsVAT` (duties on purchases, form item 10) were **completely discarded** for every filer who used them, regardless of what was entered in the (already-correct) frontend editor.
3. **Both official array fields were hardcoded to `[]`** in the builder — `OtherOperatingRevenueDtls` (form item 4A.iii, itemized "other operating revenue" rows) and `OtherIncDtls` (form item 9iii, itemized "other direct expenses" rows, per the form's own note "row can be added as per the nature of Direct Expenses") — any itemized entry a taxpayer added via the frontend's own repeatable-row editor was silently dropped before reaching the JSON.
4. **A dead lookup key**: the old builder read `amount("DutyTaxPay.TotExciseCustomsVAT")` — a literal dotted string — against a flat dict that could never contain that exact key (the mapper never produced dotted keys either), so this fallback could never match anything, on top of bug 2 already discarding the source data.
5. **Both schedules were unconditionally emitted as zero-filled stub objects** in every filing, even for a filer with no manufacturing/trading business at all (e.g. a pure-services professional) — never omitted, unlike every other genuinely optional ITR-3 schedule.

**What was fixed:**
- `app/schemas/itr3.py`: replaced both dict-bag classes with fully typed models matching the official schema exactly — `MfgOpeningInventory`/`MfgClosingStock` (Manufacturing Account, form items 1-2, all `ge=0` per the schema's own `minimum: 0` on every leaf) and a `ManufacturingAccount` wrapper; `TradingOtherRevenueEntry`/`TradingOtherIncomeEntry` (the two array row types), `TradingExciseCustomsVAT`, `TradingDutyTaxPayExciseCustomsVAT`/`TradingDutyTaxPay`, and a fully-typed `TradingAccount` (form items 4-12d). Four fields deliberately carry **no** `ge=0` constraint because the official schema itself places no minimum on them: `ManufacturingAccount.cost_of_goods_produced` (item 3, "1F − 2") and `TradingAccount.GoodsCostPrdcdFrmMA`/`GrossProfitFrmBusProf`/`IncomeIntradayTrd`/`IncomeFutureTrd` (items 11/12/12b/12d — a trading, intraday, or F&O result can be a genuine loss).
- `app/engine/draft_to_itr3_input.py`: `_business_accounts()` rewritten to walk the nested workspace structure explicitly (matching the established `_balance_sheet()`/`_audit_info()` idiom — nested `Mapping` traversal + `_decimal_value()` per leaf, not a blind flatten), including both array fields (filtered to rows with a real name, matching every other array mapper in this codebase). The now-unused generic `_decimal_map()` helper was deleted rather than left as dead code.
- `app/engine/itd/itr3.py`: `_manufacturing_account()`/`_trading_account()` rewritten to read the typed nested model directly (no more string key lookups, dotted or otherwise); both now return `{}` when the taxpayer has no data for that schedule at all (`account is None`), instead of a zero-filled stub — wired into the builder's existing "omit empty optional schedule" cleanup loop (`ManufacturingAccount`/`TradingAccount` added to the same tuple `ScheduleDPM`/`ScheduleGST`/etc. already use for this exact pattern).
- Also fixed, in the same test file, a **latent bug in ITR-3's own test suite** found immediately adjacent to this work: a test function was missing its `def test_...` line (evidently dropped during an earlier edit), causing its body to execute unconditionally as top-level module code at import time rather than run as an actual pytest test — meaning it contributed nothing to the ITR-3 test count despite appearing to. Restored as `test_itr3_mapper_prefers_workspace_audit_and_business_over_legacy_fields`; its assertions (already-passing) confirmed genuinely running as a real test post-fix (31 → 32 passed with no other change).

**Verification**: three new tests — `test_itr3_trading_account_nested_duties_and_other_revenue_rows_reach_json` (the two nested duty objects and both array fields, mapper through to JSON), `test_itr3_manufacturing_and_trading_full_schema_valid` (a fully-populated pair validated against the complete official `ManufacturingAccount`/`TradingAccount` schema definitions, not a scoped sub-check — this one passed even pre-fix, since dropping data silently doesn't make the *remaining* zero-defaulted output schema-invalid; a confirmation test, not a bug-catching one, same category as Schedule 3's `..._not_fabricates` test), and `test_itr3_manufacturing_and_trading_omitted_when_no_data` (both schedules absent from the JSON entirely for a filer with no such business). The first and third confirmed genuinely failing pre-fix via `git stash`. ITR-3 suite: 73 passed (up from 69). Full combined regression: 1328 passed, same 10-failure baseline + the one already-flagged unrelated ITR-2 regression — no new failures.
