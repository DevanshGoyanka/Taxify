# ITR-3 Schedule-by-Schedule Implementation Tracker

**This is the single source of truth for the ITR-3 schedule-wise implementation push.** Updated after every schedule is completed end-to-end. Supersedes `Docs/ITR3_V2_PIPELINE_PRODUCTION_PLAN.md` and `Docs/ITR2_ITR3_V2_PIPELINE_PRODUCTION_PLAN.md`'s Phase 8 for status purposes (their PDF↔schema reconciliation table, reproduced below, remains valid reference material and is not being redone).

## Ground rules for this push

1. **One schedule at a time, in official PDF print order** (the table below). No skipping ahead.
2. For each schedule: read the official ITR-3 form PDF section + the official JSON schema block, then implement **every mandatory and optional field** — schema → draft mapper → calculator → ITD JSON builder. A schedule is not "done" until data flows for real from a `ReturnDraft` through to schema-valid JSON, not just until the builder can serialize a hand-constructed object.
3. **Validators are explicitly out of scope for this entire push.** `app/engine/validators/itr3/` is not touched until every schedule below is done and a separate validator pass begins. Do not add, remove, or edit any ITR-3 validator rule while working through this tracker.
4. **ITR-3 only.** If a defect is found in already-shipped ITR-1/ITR-2/ITR-4 code along the way, it is flagged in the "Cross-form issues found, not fixed" log at the bottom of this document and the user is asked explicitly before anything in those forms' code is touched. Never edit ITR-1/ITR-2/ITR-4 code as a side effect of ITR-3 work.
5. Frontend work in this push is limited to what's needed for real end-to-end data flow (wiring a field to the draft, fixing a mapping bug) — **not** visual/UX redesign, which is tracked separately (`Docs/FRONTEND_UI_UX_REDESIGN_AUDIT_AY2026_27.md`) and deliberately deferred.
6. After each schedule: run the full regression suite, confirm no new failures beyond the established baseline, update this tracker's status table and add a dated "Fix status" note under that schedule, then commit.

## Schedule-by-schedule fix log

### Schedule 1 — Personal Information (A1–A18) — ✅ closed 2026-09-17

**What was found** (comparing `Docs/ITR3_FIELD_BY_FIELD_GUIDE_1_PERSONAL_INFO_TO_HP.md` §1 and the official schema's `PersonalInfo`/`AlternateAddress` definitions directly against `app/engine/itd/itr3.py::_parta_gen1`):
- A6a (building/village name) and A7a (road/street) were captured nowhere — the builder hardcoded `ResidenceName`/`RoadOrStreet` to `""` unconditionally.
- A16 (Aadhaar) was read by `_parta_gen1`'s signature but never actually sourced from `ITR3Input` in the canonical path — always absent from real filings.
- A17's office/residence phone (schema `Address.Phone`) had no code path at all; its secondary-mobile columns (`CountryCodeMobileNoSec`/`MobileNoSec`) were hardcoded to `0`/`0` unconditionally.
- A18's secondary email (`EmailAddressSec`) was never emitted.
- **A5b–A13b, the "Secondary Address"**: `SecondaryAdd` was hardcoded `"N"` regardless of the taxpayer's actual declaration, and — the most serious finding — whenever `secondary_add == "Y"` was forced via a non-canonical caller, `AlternateAddress` was populated as a **literal copy of the primary address**, not real secondary-address data. There was no source data path for a genuine alternate address anywhere in the pipeline.
- Root cause for all of the above: `app/schemas/itr3.py`'s `ITR3Input` had no fields at all for any of this (only the eight primary-address scalars), and `app/engine/draft_to_itr3_input.py` never read the corresponding `ReturnDraft.personal.*` fields — even though every one of those fields (`aadhaar`, `secondaryEmail`, `secondaryMobile`(+country code), `landlineStdCode`/`landlinePhoneNo`, `residenceName`, `roadOrStreet`, `secondaryAddressDifferent`, `alternateAddress`) already existed on the shared `PersonalInfo` draft model. **No frontend/draft-schema changes were needed** — this was purely a backend mapper + builder gap.

**What was fixed:**
- `app/schemas/itr3.py`: added `residence_name`, `road_or_street`, `zip_code`, `mobile_country_code`, `assessee_aadhaar`, `office_phone_std_code`, `office_phone_no`, `secondary_mobile_country_code`, `secondary_mobile_no`, `secondary_email`, `secondary_address_different`, and the nine `alternate_*` fields to `ITR3Input`.
- `app/engine/draft_to_itr3_input.py`: mapped all of the above from `draft.personal.*`/`draft.personal.alternateAddress.*` (soft/optional, matching the mapper's existing style for this section — hard requiredness stays the builder's job, as it already was for the original 8 fields).
- `app/engine/itd/itr3.py`: `_parta_gen1()`/`build_itr3_json()` rewritten to emit every field for real: `ResidenceName`/`RoadOrStreet` from sourced data; `AadhaarCardNo` from the typed input; `Address.Phone` emitted only when a real STD code + number exist; secondary mobile/email sourced for real; `SecondaryAdd` reflects the taxpayer's actual flag; `AlternateAddress` built from genuinely distinct secondary-address data, never copied from the primary address. Added a fail-closed check: if `secondary_address_different` is True but the required alternate-address fields weren't actually sourced, `build_itr3_json` now raises rather than silently omitting or fabricating the block. `AlternateAddress.PinCode`/`ZipCode` are only emitted when real (neither is schema-required — no fabricated PIN default was introduced for the new code, unlike the pre-existing primary-address fallback which was left as dead-path legacy scaffolding, see below).
- Deliberately **not** touched: the primary `Address`'s existing fabricated-default kwargs (`locality: str = "Locality"`, `pin_code` falling back to `110001`, etc.) on `build_itr3_json`'s legacy (`typed_input=None`) call path — every real canonical caller already passes `typed_input`, which hard-requires these via the pre-existing `required_identity` check before `_parta_gen1` is ever reached, so this fallback code is effectively dead in production; changing pin_code's required-ness policy (e.g. to support a foreign-only ZIP-code address) is a separate design decision, not evidenced as broken today, and was left alone to keep this fix scoped to real field-completeness, not a required-ness policy change.

**Verification**: two new tests in `tests/test_itr3_canonical_foundation.py` — `test_itr3_personal_info_optional_fields_reach_typed_input_and_json` (every new field set on a realistic draft, asserted present in both `typed_input` and the emitted JSON, validated against the official `PersonalInfo` schema sub-definition directly via `jsonschema.Draft4Validator` — scoped to this schedule since the full document doesn't validate yet yet, pending Schedules 5/8/9/25/26/24 etc.) and `test_itr3_secondary_address_flag_without_data_fails_closed` (confirms the new fail-closed guard). Both confirmed genuinely failing pre-fix via `git stash`. Full combined regression (`test_itr1/2/3/4_*.py` + filing-gateway/AMT/CYLA/BFLA/capital-gains suites): 1313 passed, same 10 pre-existing baseline failures plus the one already-flagged, pre-existing, unrelated ITR-2 regression (see "Cross-form issues" above) — no new failures.

**Correction found during Schedule 2 work (2026-09-17), applied retroactively to Schedule 1**: while reading ITR-2's own `_part_a_gen1`-equivalent builder as a reference, found a live-UAT-verified fact ITR-2's own code comment documents (2026-09-13, PAN GOYPT2026A): ITD's real Type-2 `validateItr` **rejects an entirely-absent `AlternateAddress` block**, regardless of the `SecondaryAdd` flag's value — even though neither is schema-required. Schedule 1's original fix omitted `AlternateAddress` whenever the taxpayer had no genuinely distinct secondary address, which — since ITR-3 shares the identical `PersonalInfo`/`AlternateAddress` schema shape with ITR-2 — would almost certainly hit the same live rejection. Revised to match ITR-2's proven fallback exactly: `SecondaryAdd` is now always `"Y"`, and `AlternateAddress` is always emitted, falling back to a copy of the primary address when no genuinely distinct one exists (the fail-closed guard for "declared different but didn't provide one" stays). Also found and fixed, while reading the schema's `Status` enum for A14: `assessee_status` (A1-A18's own Individual/HUF flag) was **never wired at all** — `build_itr3_json` never derived it from `typed_input`, so every canonical filing silently emitted `"I"` regardless of the real `draft.personal.assesseeStatus`. Added `ITR3Input.assessee_status`, mapped from the draft, and wired into the canonical builder path. Both corrections covered by `test_itr3_no_secondary_address_still_emits_alternate_address_as_primary_copy` (new) and the existing Schedule 1 tests, all confirmed passing; full detail in the Schedule 2 entry below.

### Schedule 3 — Audit Information (A20) — ✅ closed 2026-09-17

**What was found**: `AuditInfo` (both the `app/schemas/itr3.py` typed model and the `_parta_gen2()` builder) covered only 5 of roughly 25 real schema fields. Two of those five weren't even real: `AgrOFAllAmtsRcvd`/`AgrOFAllPayMade` (A20(a2ii)/(a2iii), the cash-receipt/payment percentage question that determines whether a mid-size taxpayer is 44AB-liable) were **hardcoded to `"Upto5Per"` unconditionally**, regardless of the actual return — a return where the real answer was "more than 5%" (the answer that actually *triggers* audit liability) would have silently disclosed the wrong, audit-avoiding answer. `app/schemas/return_draft.py`'s `ITR3AuditInfo` (plus its two row types, `OtherAuditReportEntry` and `AuditUnderOtherActEntry`) already captures every one of these fields in full — confirmed, as with Schedules 1-2, this was purely a backend mapper + builder gap, no frontend work needed.

- `app/schemas/itr3.py`: extended `AuditInfo` from 5 to 24 fields, covering the full A20(a)-(e) list.
- `app/engine/draft_to_itr3_input.py`: `_audit_info()` rewritten to extract every field from both of this mapper's existing two data sources — the raw official-schema-shaped "workspace" object (`draft.itr3BusinessWorkspace.core["PartA_GEN2"]["AuditInfo"]`, when a UI editor has written directly in CBDT shape) and the canonical typed `draft.itr3AuditInfo` fallback — matching the dual-path pattern this function already had for the 5 original fields, just extended to the other 19.
- `app/engine/itd/itr3.py`: `_parta_gen2()` rewritten to emit every field for real, each one only when the taxpayer's actual data supports it (the audit-report detail block only when `audited_by_accountant` is true; the 92E detail only when both the date and acknowledgement number are genuinely present; both array tables built from real entries, empty rows filtered out) — never fabricated, matching this schedule's own "omit, don't guess" discipline. Also fixed the `AuditAccountantFlg` field, which was previously wired to `audit.account_audited` (the SAME boolean already used for the separate, differently-named `AccountAuditFlag` field) — now correctly reads the draft's own distinct `audited_by_accountant` fact.

Full combined regression: 1319 passed, same 10-failure baseline + the one already-flagged unrelated ITR-2 regression — no new failures.

### Schedule 4 — Nature of Business or Profession — ✅ closed 2026-09-17

**What was found**: a small schedule (just `Code`/`TradeName1`/`Description` per row), but with two real bugs, not just a completeness gap.
1. **`TradeName1`** ("Trade name of the proprietorship, if any") was captured on the draft (`ITR3NatureOfBusiness.tradeName`) but had **no field on the typed `NatureOfBusiness` schema at all**, and both mapper code paths silently dropped it — confirmed directly: the pre-existing test `test_itr3_builder_maps_parta_gen2_workspace` had been setting `tradeName="Tech"` on its own test draft since before this push and never noticed it never reached the output, because the test never asserted on that field.
2. **Three legitimate CBDT business-nature codes were silently dropped from every return that used them.** The official schema enum includes three disambiguation codes with an `_N` suffix — `16019_1` ("Medical Profession", distinct from the base `16019`), `20023_1` ("Sports Management"), `21008_1` ("Event Management"). Both the mapper's row filter (`row.code.isdigit()` / `str(...).isdigit()`) and the typed `NatureOfBusiness.code` field's own Pydantic pattern (`^[0-9]{5}$`) rejected any code containing the underscore — meaning a doctor, sports manager, or event manager correctly selecting their actual, official business-nature code would have that row either silently filtered out of the mapped list, or (if constructed directly) fail Pydantic validation outright.

**What was fixed:**
- `app/schemas/itr3.py`: `NatureOfBusiness.code`'s pattern widened to `^[0-9]{5}(_[0-9]+)?$`; added the missing `trade_name` field.

### Schedule 13 — Schedule HP (House Property) — ✅ closed 2026-09-18

**What was found**: no existing test file referenced Schedule HP at all before this push (confirmed by grep), which explains why the most severe defect here — a genuine, reproducible **crash**, not just a wrong value — had never surfaced. Four real defects, found by validating a realistic co-owned property against the live official schema directly rather than trusting the builder's apparent completeness:

1. **A crash bug**: `AsseseeShareProperty` (the property's own ownership-share percentage, form item 1f's multiplier) is an official schema `"number"` field with `multipleOf: 0.01` — but the builder emitted `source.assessee_share_percent` as a raw `Decimal` object, unconverted. `jsonschema`'s `multipleOf` check computes `instance / dB` where `dB` is always a plain Python `float` (loaded from the schema JSON) — dividing a `Decimal` by a `float` raises `TypeError` outright. This meant **official schema validation would crash, not merely fail, for every single Schedule HP property this codebase has ever built** (the field is unconditionally emitted for every row, co-owned or not).
2. **A data-corruption bug**: `PercentShareProperty` (each co-owner's own share, same `multipleOf: 0.01` percentage type) was being run through `_official_integer_tree()`, which blindly converts every `Decimal` via `_to_rupees()` — a money-only whole-rupee rounding helper. A legitimate co-ownership split like 37.5% would have been silently rounded to a whole number, corrupting real ownership-share data.
3. **A schema-violation bug**: optional identity fields on `CoOwners`/`TenantDetails` (`PAN_CoOwner`/`Aadhaar_CoOwner`/`PANofTenant`/`AadhaarofTenant`/`PANTANofTenant`) were being emitted as literal JSON `null` when absent, rather than omitted — `_official_integer_tree()` passes `None` through unchanged, and these fields are typed `{"type": "string"}` in the schema with no `"null"` variant, so a present-but-null key fails validation.
4. **`PassThroghIncome`** (form item 2) was hardcoded to `0` unconditionally, discarding any real Schedule-PTI house-property-head income — even though `typed_input.pti_entries` is already mapped from the draft (confirmed by grep; no cross-schedule dependency on Schedule PTI's own not-yet-closed work, tracker row #47) and the form's own note explicitly calls for exactly this ("include ... Pass-through income referred to in schedule PTI").

All four had an exact, already-proven fix already shipped in `app/engine/itd/itr2.py::_schedule_hp()` (`float()` conversion for both percentage fields, a `{k:v for k,v in {...}.items() if v is not None}` filter for the optional identity fields, and CBDT rule #79's `PassThroghIncome` = HP-head `pti_entries` sum) — ported directly rather than re-derived, since ITR-2 and ITR-3 share the identical `ScheduleHP` schema shape.

**What was fixed:**
- `app/engine/itd/itr3.py`: `_schedule_hp()` now converts `AsseseeShareProperty`/`PercentShareProperty` via `float()`, filters `None`-valued optional keys out of every `CoOwners`/`TenantDetails` row instead of emitting them as `null`, and computes `PassThroghIncome` from `typed_input.pti_entries` filtered to `income_head == "HP"` (CBDT rule #79).
- `app/schemas/itr3.py`: `ITR3ScheduleHPProperty` gained `property_owner: Literal["SE","MI","SP","OT"]` and `property_type: Literal["L","D","S"]` (matching the official enums exactly — the draft's own `PropertyOwnerType`/`PropertyType` literals already only produce these values, confirmed by inspection, so this tightening rejects nothing legitimate), `ge=0,le=100` on `assessee_share_percent`, and `ge=0` on every money field the schema itself bounds at zero (`annual_lettable_value`/`rent_not_realized`/`local_taxes`/`standard_deduction`/`interest_on_loan`/`arrears_unrealised_rent`) — `annual_value_owned`/`income_of_hp` deliberately kept unbounded below, matching the schema's own lack of a minimum (a let-out property can show a genuine loss).

**A tooling limitation found and documented, not "fixed"**: `jsonschema`'s `Draft4Validator` `multipleOf` check has a known floating-point-precision quirk — for some two-decimal percentage values (e.g. `33.33`), `value / 0.01` lands on `3332.9999999999995` in IEEE-754 binary rather than exactly `3333`, producing a false-positive "not a multiple of 0.01" rejection on a value that genuinely is one. This affects this codebase's *local validation tooling* (and, by the identical `float()` pattern, ITR-2's own already-shipped code carries the same latent quirk for unlucky percentage values) — it is not a defect introduced by this fix, and no reliable Python-side workaround exists without a fragile epsilon comparison. Documented here rather than silently worked around; the new regression test deliberately uses `62.5`/`37.5` (still genuinely fractional, proving real precision preservation) instead of a value that happens to trip this specific tool quirk.

**Verification**: two new tests in `tests/test_itr3_canonical_foundation.py` — `test_itr3_schedule_hp_full_schema_valid_with_fractional_co_owner_share` (a co-owned, let-out property with a fractional ownership split and a tenant with no PAN/Aadhaar, validated against the complete official `ScheduleHP` definition, confirming both the percentage precision and the omitted-not-null identity fields) and `test_itr3_schedule_hp_pass_through_income_from_pti_entries` (two PTI entries, one HP-head and one OS-head; confirms only the HP-head amount reaches `PassThroghIncome`). Both confirmed genuinely failing pre-fix via `git stash` (the first with the exact pre-fix crash/rounding defects, the second with `0 == 15000`). ITR-3 suite: 85 passed (up from 83). Full combined regression: 1340 passed, same 11-failure baseline — no new failures. No ITR-3 validator touched; no ITR-1/2/4 code touched (ITR-2's logic was read and ported, not modified).
