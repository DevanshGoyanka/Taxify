B-01  Wrong
Fake TAN "DELA00001A" hardcoded as fallback in both ITR-1 and ITR-4 builders
When a TDS entry in the input doesn't carry a TAN, the JSON builder falls back to the fabricated value DELA00001A. The ITD portal validates every TAN against its deductor registry — a non-existent TAN causes a hard portal rejection of the entire filing. The right fix is to make TAN a required field on the TDS entry schema and surface the validation error before building the JSON.
app/engine/itd/itr1.py:1218, 1241 app/engine/itd/itr4.py:2292, 2314
B-02  Missing
/itr1/compute-json does not call validate_itr1_json() — ITR-4 does, ITR-1 doesn't
itr1_schema.py exports validate_itr1_json() which runs the generated JSON against the official CBDT schema. The /itr4/compute-json route calls the equivalent validate_itr4_json() (itr.py:523). The /itr1/compute-json route (itr.py:329–383) performs no such step — schema-invalid JSON is silently returned and would fail at the ITD portal. One import and one call is the fix.
app/routers/itr.py:329–383 app/engine/itd/itr1_schema.py:45
B-03  Partial
Children education & hostel allowance hardcoded to num_children=0 — always ₹0 for everyone
The salary schedule computes Section 10(14) child exemptions by calling _exempt_children_education(allowance, 0) and _exempt_hostel(allowance, 0) — literally passing 0 as the child count. The comment in the code confirms this: "the schema does not yet have a dedicated field, so default to 0 children (i.e., exemption = 0)". Any taxpayer with children claiming ₹100–₹300/month per child gets zero exemption, inflating their taxable salary.
app/engine/schedules/salary.py:154–158
B-04  Missing
~50 ITR-1 CBDT portal validation rules unimplemented
Your own REMAINING_ITEMS_TO_IMPLEMENT.md documents these explicitly. Notable missing rules: Rules 31–42 (exempt income dropdown uniqueness), 44–46 (HP annual value computations), 66–73 (exempt allowance limits), 78–87 (80G donee PAN validation), 261–263 (HRA exemption schedule detail), 295–300 (co-ownership validations). The ITD portal runs its own rule engine on uploaded JSON and rejects on any failed rule. Passing your API's validation does not mean the portal will accept it.

B-05  Missing
~40 ITR-4 CBDT portal validation rules unimplemented
Same problem as B-04 for ITR-4 (Sugam). Missing rules include 44AD/44ADA/44AE turnover limit cross-checks, HP co-ownership, 80G PAN validation, and exempt income dropdown uniqueness. Filing a return that passes your validator but fails the portal's rule engine leaves the taxpayer with a non-filed status and a confusing error from the ITD portal.

B-06  Missing
GST Schedule absent from ITR-4 — any GST-registered presumptive taxpayer cannot properly file
ITR-4 requires a GSTIN-wise turnover schedule for any taxpayer with a GSTIN. The REMAINING_ITEMS_TO_IMPLEMENT.md explicitly lists "GST Schedule — Not implemented". The builder does emit TurnoverGrsRcptForGSTIN as an empty array with a zero total, which means GSTIN data is silently dropped rather than reported. A GST-registered 44AD/44ADA assessee filing through Taxify will produce a non-compliant JSON.
app/engine/itd/itr4.py:734–756 Docs/REMAINING_ITEMS_TO_IMPLEMENT.md
B-07  Missing
HRA Schedule 10(13A) computation detail absent from ITD JSON output
CBDT rules 261–263 require the Schedule 10(13A) breakdown (city category, actual HRA received, rent paid, 10%-of-salary threshold) in the JSON. Taxify accepts hra_exempt_amount as a user-entered figure and passes it through, but never builds the schedule backing it. The ITD portal will reject filings where the HRA exemption is claimed without the corroborating schedule details. This affects a large proportion of salaried ITR-1 filers.
app/engine/itd/itr1.py (no Schedule 10_13A builder) app/schemas/itr1.py (hra_exempt_amount is user-input, no schedule fields)
High

Incorrect tax logic or missing required fields

Will produce wrong tax figures or cause portal failures for specific taxpayer profiles.

H-01  Wrong
80CCD(2) statutory cap silently bypassed when salary base is zero
In section_80ccd2.py:64: ceiling = (salary * pct) if salary > 0 else user_claim. When no salary base is provided the ceiling collapses to the user's own claim — making it a no-op cap. A taxpayer claiming ₹5L in employer NPS with ₹0 salary on record gets the full ₹5L deduction instead of ₹0. The caller in itr1.py passes salary correctly, but the fallback logic itself is wrong and will corrupt results for any edge case where the salary field is absent.
app/engine/schedules/deductions/section_80ccd2.py:64
H-02  Wrong
SECTION_80CCD2_LIMIT annotated "No upper limit" — misrepresents the statute
constants.py:171 declares SECTION_80CCD2_LIMIT: Final[Decimal] = None with the comment "No upper limit". The section absolutely has a ceiling (10% or 14% of salary). This misleading constant invites future developers to skip the cap entirely if they import it. The constant should be removed or replaced with the two percentage constants that already exist in section_80ccd2.py.
app/engine/constants.py:170–171
H-03  Missing
AadhaarCardNo field missing from ITR-1 schema and CBDT JSON output
The CBDT ITR-1 JSON schema requires AadhaarCardNo (or an Aadhaar enrolment ID). Your REMAINING_ITEMS_TO_IMPLEMENT.md lists it as a known gap. Without it the generated JSON is structurally incomplete and will fail schema validation at the ITD portal for any taxpayer whose Aadhaar is seeded with PAN.
app/schemas/itr1.py (field absent) Docs/REMAINING_ITEMS_TO_IMPLEMENT.md
H-04  Partial
SeventhProvisio139 declared but triggering-threshold logic absent
The schema accepts a seventh_provisio_139 string field, but nowhere does the engine check whether the three statutory triggers are actually met: bank deposits > ₹1 Cr, foreign travel > ₹2 L, or electricity consumption > ₹1 L. A taxpayer who crosses one of these thresholds but doesn't set the flag manually will be non-compliant. This must be auto-derived from other input fields, not left to the user.
app/schemas/itr1.py:1434 app/engine/validators/itr1/input_rules.py (no threshold check)
H-05  Duplication
Two separate ERI route sets wired — divergence risk when one is updated
/api/v1/eri/* routes live in integration.py and /eri/* routes live in eri.py. Both are mounted in main.py. Both handle ERI login, add-client, prefill, e-verify, and acknowledgement. The README acknowledges this as "known duplication." Each update to ERI business logic must be applied in two places or the routes diverge. In production with real ERI credentials, a silent divergence means one path files correctly and the other doesn't.
app/routers/integration.py (/api/v1/eri/*) app/routers/eri.py (/eri/*) app/main.py (both mounted)
H-06  Partial
Test suite is at 177 failures + 13 collection errors — zero regression safety net
The README documents this baseline. With no green tests, every bug fix or feature addition has no automated check confirming it didn't break something else. In a tax engine where a one-line constant change can swing a taxpayer's liability by lakhs, this is a production risk. The collection errors mean some test modules cannot even be imported, which likely means the real failure count is higher.
README.md (Running Tests section) tests/ (all)
H-07  Partial
PDF download is a lightweight summary, not a CBDT acknowledgement or ITR-V
The download-pdf endpoint emits a simple reportlab-generated text summary of stored form_data. It explicitly states in its docstring: "A full CBDT-compliant PDF should be generated from the canonical engine result." Taxpayers expect the ITR-V acknowledgement from this endpoint. If CA practices are presenting this to clients as the filed document, it will cause confusion and compliance issues.
app/routers/client_itr.py:251–288
H-08  Security
CORS configured with allow_methods=["*"] and allow_headers=["*"] with credentials allowed
Combining allow_credentials=True with wildcard methods and headers is overly permissive and creates CSRF surface. Since the API handles real taxpayer PII and ERI credentials, the CORS policy should explicitly enumerate the allowed methods (GET, POST, PUT, DELETE) and headers (Authorization, Content-Type) rather than passing everything through.
app/main.py:130–133
Medium

Maintenance & correctness debt

Won't cause immediate portal rejection but will create support burden or silent errors for edge cases.

M-01  Duplication
/tax-summary/compute and /api/tax/compute are duplicate routes for the same handler
Two aliased routes with no deprecation path — any future change to the handler must be tested against both URLs, and API consumers don't know which to use.
app/routers/tax.py
M-02  Security
PORTAL_ENCRYPTION_KEY is optional — missing key silently stores portal passwords in plaintext
If the env var is absent at deployment, Fernet encryption is bypassed and client ITD portal passwords are stored as plaintext in SQLite. On a shared EC2 instance this is a significant PII risk. The key should be required at startup.
app/schemas/security/portal_crypto.pyREADME.md (Environment Variables)
M-03  Missing
80G donee PAN validation not implemented — HIGH priority per your own docs
Rules 78–87 require PAN-level validation of 80G donee institutions. Marked HIGH priority in REMAINING_ITEMS_TO_IMPLEMENT.md. Incorrect 80G donations inflate deductions and can trigger scrutiny.
Docs/REMAINING_ITEMS_TO_IMPLEMENT.md (Rules 78–87)
M-04  Missing
IFSC code validation absent — Rule 107 requires RBI-database check for non-cash donations
Any 80G donation via bank transfer requires a valid IFSC. Currently any string passes. An invalid IFSC will cause a portal rejection for donation-heavy returns.
Docs/REMAINING_ITEMS_TO_IMPLEMENT.md (Rule 107)
M-05  Missing
Co-ownership property validations (Rules 295–300) absent
Co-owned house property requires cross-owner income splitting and co-owner Aadhaar/PAN fields. These validations are listed as HIGH priority gaps. A co-owner claiming 100% income on an ITR-1 will be flagged in scrutiny.
Docs/REMAINING_ITEMS_TO_IMPLEMENT.md (Rules 295–300)
M-06  Partial
ITR-2 and ITR-3 compute-json routes are callable but engines have major known gaps
Both /itr2/compute-json and /itr3/compute-json are live and authenticated. ITR-2 lacks Schedule FSI, FA, 5A, ESOP, PTI. ITR-3 lacks PartA_OI, PartA_QD, ScheduleGST, ScheduleDCG, ScheduleUD. These endpoints should return 501 until those gaps are closed, not silently emit incomplete JSON.
app/routers/itr.py:386–469
M-07  Partial
Automation modules marked standalone but partially wired into API via integration router
The README says app/automation/ is "NOT wired to API" — but integration.py imports parts of it for 26AS parsing. This creates a hidden runtime dependency: if automation's Playwright dependencies are absent, the 26AS import endpoint fails with an ImportError in production.
app/routers/integration.py (/integration/26as/import)app/automation/ (ais_converter, as26_converter)
M-08  Missing
Exempt income dropdown uniqueness (Rules 31–42) not enforced
CBDT rules require that each exempt income nature code appears only once in the Schedule EI listing. Duplicates cause a portal rule-engine rejection. No uniqueness check exists in the validator.
app/engine/validators/itr1/input_rules.py
M-09  Missing
No rate limiting on any API endpoint
A single-worker uvicorn on a t3.micro with no rate limiting means auth endpoints (/auth/login, /auth/signup) are open to credential stuffing, and compute endpoints that invoke the Playwright/PDF stack can be abused to exhaust the instance. Given real taxpayer PII is held, even basic token-bucket rate limiting on auth routes is needed.
app/main.py (no rate limit middleware)

L-01  Duplication
saved_return table (legacy /returns/* endpoints) is orphaned from the client workflow
Two parallel return-storage models exist: client_itr (client-scoped, the real workflow) and saved_return (user-scoped legacy). Both are live. Confusion about which one "matters" leads to incorrect dashboard counts and orphaned records.

L-02  Security
JWT has no refresh token — 24h tokens cannot be revoked
If a token is leaked (e.g., via a support ticket), it remains valid for up to 24 hours with no mechanism to revoke it. Given the PII sensitivity, consider a shorter expiry + refresh token pattern or a token denylist.
